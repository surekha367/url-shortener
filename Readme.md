https://www.example.com/products/electronics/mobile-phones/samsung-galaxy-s25?color=black&storage=256gb

-> shortened url
https://short.ly/aB72x

the shortner url just acts as a pointer/reference to the original url.

# Production-Grade URL Shortener

A URL shortener built with **Python, FastAPI and PostgreSQL**. It turns a long link into a short 6-character link, redirects visitors to the original page, and (in later milestones) records click analytics, caches hot links, and rate-limits abuse.

## How it works

**Flow 1: Create a short link (write flow)**
A client sends a long URL. The server generates a unique 6-character code, saves the pair in the database, and returns the short link.

**Flow 2: Open a short link (read flow)**
A browser requests `/{code}`. The server looks up the code and replies with a redirect (a status code plus a `Location` header). The **browser** then makes the second trip to the original page itself.

The read flow happens far more often than the write flow: a link is created once but may be clicked millions of times. This single fact drives most of the "production-grade" decisions (caching, background click recording, rate limiting).

## API design

### `POST /api/links` : create a short link

| | |
|---|---|
| **Input** | `original_url` (required): valid http/https URL, max 2,048 characters |
| | `expires_at` (optional): timezone-aware datetime in the future. Empty means the link never expires |
| **Success** | **201 Created** with `code`, `short_url`, `original_url`, `created_at`, `expires_at` (all times in UTC) |
| **Errors** | **422**: invalid or too-long URL, scheme is not http/https, URL points to our own domain, `expires_at` has no timezone offset or is in the past |
| | **500**: all retry attempts to generate a unique code failed (logged) |

The caller's identity is **never** taken from the request body. After login is added, it comes from the auth token.

### `GET /{code}` : redirect

| Situation | Status | `Location` sent? | What the visitor sees |
|---|---|---|---|
| Valid and active | **302** | Yes (plus `Cache-Control: no-store`) | The destination page |
| Wrong code shape | **404** | No | "Link not found" page |
| Code never existed | **404** | No | "Link not found" page |
| Deleted (`deleted_at` set) | **410** | No | "This link was removed" page |
| Expired (`expires_at` in the past) | **410** | No | "This link has expired" page |

**Check order (cheapest first):** shape, then database lookup, then deleted?, then expired?, then redirect.

**Shape rule:** a code is valid only if it is exactly 6 characters and every character is in `0-9`, `a-z` or `A-Z`. Anything else returns 404 immediately, without a database query.

Errors on `/{code}` are **HTML pages** (a human is using a browser). Errors on `/api/...` are **JSON** (a program is calling).

## Database design

### `urls`

| Column | Type | Rules |
|---|---|---|
| `id` | BIGINT | Primary key, generated by the database |
| `code` | VARCHAR(6) | NOT NULL, **UNIQUE**, case-sensitive |
| `original_url` | TEXT | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL, default now |
| `expires_at` | TIMESTAMPTZ | Nullable (empty = never expires) |
| `deleted_at` | TIMESTAMPTZ | Nullable (empty = active) |

`user_id` (nullable INTEGER, foreign key to `users`, indexed) is **added in the login milestone through a new migration**, because the `users` table does not exist yet.

### `clicks` (created at the click-tracking milestone)

| Column | Type | Rules |
|---|---|---|
| `id` | BIGINT | Primary key |
| `url_id` | BIGINT | NOT NULL, foreign key to `urls.id` |
| `clicked_at` | TIMESTAMPTZ | NOT NULL, default now |
| `user_agent` | TEXT | Nullable |
| `referrer` | TEXT | Nullable |
| `ip_hash` | VARCHAR | Nullable (a hash, not the raw IP, for privacy) |

**Index:** one composite index on (`url_id`, `clicked_at`). It answers both "all clicks for this link" and "clicks per day for this link".

### `users` (created at the login milestone)

`id`, `email` (unique), `password_hash` (never the password itself), `created_at`.

**Index note:** primary keys and UNIQUE constraints are indexed automatically in PostgreSQL. **Foreign key columns are not**, so `clicks.url_id` and `urls.user_id` need their own indexes.

## Design decisions and reasons

| Decision | Options considered | Chosen | Why |
|---|---|---|---|
| **Redirect type** | 301 vs 302 | **302** with `Cache-Control: no-store` | A cached redirect lets the browser skip our server, so those clicks are never counted. An experiment on a real shortener showed that the *caching headers*, not just the status code, decide this. |
| **Code generation** | UUID, hash of URL, sequential ID + base62, random | **Random 6 characters** from 62 symbols, generated with `secrets` | 62^6 is about 56.8 billion codes, so collisions and guessing are both very unlikely. A UUID is too long. A hash gives the same code for the same URL, which breaks per-user stats and expiry. Sequential IDs are guessable, so someone could loop through every link. |
| **Uniqueness** | Check in Python, or database constraint | **UNIQUE constraint** plus **bounded retry** (3 to 5 attempts) | A Python check fails when two requests arrive at the same moment; the database cannot be fooled. Retrying silently is better than showing an error for a rare problem the user cannot fix. After the retries run out, return a 5xx and log it. |
| **Base62** | Use or skip | **Skipped** for random codes | Base62 turns *numbers* into short text, so it is only needed for sequential IDs. It is encoding, not security. |
| **Random source** | `random` vs `secrets` | **`secrets`** | `random` is predictable if its internal state is learned. Codes are what a stranger would try to guess. |
| **Custom aliases** | Allow or not | **Not in version 1** | Avoids "already taken" and reserved-word conflicts (for example `docs`). Can be added later. |
| **Clicks storage** | Counter in the link row vs one row per click | **Separate `clicks` table, count rows** | A single counter row becomes a bottleneck on viral links and can lose updates under concurrency. Start simple, optimize after measuring. |
| **Primary key** | Code as PK vs numeric ID | **BIGINT `id` + unique `code`** | Smaller, faster foreign keys for millions of click rows, and the code can change without touching other tables. |
| **Deletion** | Hard vs soft delete | **Soft delete** (`deleted_at`) | Keeps click history, allows 410, prevents code reuse (an old QR code will not point to someone else's page), and can be undone. Cost: every query must exclude deleted rows. |
| **Missing / gone links** | 404 for everything, or 404 + 410 | **404** never existed, **410** expired or deleted | Clearer message for visitors and easier debugging. |
| **URL validation** | Fetch the URL to check it, or validate its shape | **Validate the shape** (`HttpUrl`, http/https only, max 2,048 chars) | Fetching is slow, unreliable, and risks SSRF attacks. Rejecting `javascript:` stops script-injection redirects. |
| **Self-redirect** | Allow or reject | **Reject** URLs on our own domain | Prevents redirect loops. |
| **Time handling** | Local time, duration, exact time | **Exact datetime with offset, stored and returned in UTC** | No timezone guessing on the server. Datetimes without an offset are rejected. |
| **Identity** | `user_id` in request body vs from token | **From the login token only** | A body field would let anyone create links as someone else. |
| **Domain config** | Hardcoded, request Host header, environment variable | **Environment variable** (`BASE_URL`) | The Host header can be faked, and the address differs between laptop and deployment. |
| **Error format** | JSON vs HTML | **HTML for `/{code}`, JSON for `/api/...`** | Respond in the format the caller understands. |
| **Route conflicts** | Rely on route order, or separate namespace | **All management endpoints under `/api`** plus the shape check | `/{code}` matches any path, so a separate prefix prevents clashes. |
| **`user_id` column** | Create `users` table early, or add the column later | **Add later by migration** | The foreign key needs the `users` table to exist. Building only what each milestone needs also practises migrations. |

### Two caches, not to be confused

- **Browser cache:** skips our server entirely, so clicks are lost. Disabled with no-cache headers.
- **Redis cache (milestone 8):** only speeds up the code-to-URL lookup. Our server still runs, so clicks are still recorded.

### Open questions (to decide at the relevant milestone)

- Should a click be saved before replying (slower, safer) or after, in the background (faster, a click can be lost on a crash)?
- Login required to create links, or anonymous creation allowed? (Leaning: require login eventually.)
- Counting clicks by rows vs a cached counter, once traffic justifies it.

## Configuration

All environment-specific values live in a `.env` file that is **not** committed to Git.

| Setting | Purpose |
|---|---|
| `BASE_URL` | Scheme + host + port used to build short links and detect self-redirects (`http://localhost:8000` locally) |
| `DATABASE_URL` | PostgreSQL connection |
| `MAX_CODE_RETRIES` | Attempts to generate a unique code before returning 500 |
| `CODE_LENGTH` | Length of the short code (6) |
